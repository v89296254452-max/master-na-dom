# Production Memory Audit — master-na-dom.online

Дата: 2026-09-16. Проведено после инцидента с ростом RSS Node-процесса и
restart-loop PM2 (см. предыдущий инцидент-репорт в истории чата). Задача этого
документа — найти точную архитектурную причину, а не считать её очевидной.

**Методология:** все выводы в разделах 1-7 основаны либо на прямых измерениях
(нагрузочный тест на изолированном инстансе :3001, никогда не подключённом к
nginx upstream и не видимом снаружи), либо на чтении реального кода/конфигов
production. Там, где вывод — оценка/экстраполяция, а не измерение, это явно
помечено.

## 3-5. Контролируемый нагрузочный тест (Этапы 4-5)

**Где:** изолированный процесс `next start -p 3001`, слушающий только
`127.0.0.1:3001`. Ни разу не добавлялся в nginx upstream — публично недоступен,
production (`:3000` за nginx) ни разу не трогался этими тестами. Использовался
тот же build/данные, что и production (та же директория `.next`, та же
`ai-content.db`) — то есть тест максимально честный к реальному коду, не
синтетический мок.

**Инструмент:** вместо `--require`-пробника (не сработал — Next.js
re-exec'ает себя в дочерний процесс, и `NODE_OPTIONS` не долетает до
реального сервера, см. ниже) — прямой опрос `/proc/<pid>/status` (`VmRSS`)
каждые 0.2-0.3с внешним скриптом.

### Сценарий D (упрощённый) — один и тот же URL, concurrency 10, n=200
`p50=37ms, p95=1424ms (первый прогрев соединений), codes: 200×200`. Не измерял
RSS отдельно для этого прогона (шёл первым, база для дальнейших).

### Сценарий B — 900 НИКОГДА не рендерившихся валидных гео/бренд URL, concurrency 30
(инстанс уже ~20 минут не холодный, RSS до теста = 342.1 MB)

| Момент | RSS |
|---|---|
| До теста | 342.1 MB |
| Пик во время теста (41 сек, 900 запросов) | **518.9 MB** |
| Траектория во время | пилообразная: 400→471→441(GC)→506→462(GC)→509→468(GC)... — классическая работа V8 GC под нагрузкой, не монотонный рост |
| Сразу после (0-23с) | плато 469.1 MB |
| Через 27.7с после конца теста | **372.9 MB** — память вернулась почти к исходной |

### Повторный тест с ИСТИННО холодным стартом (Этап 4, "cold restart")
Новый процесс, RSS на старте = **195.1 MB**. Сразу — 1200 новых уникальных URL
(гео+бренд+часть из problem-cluster, из которых валидными по этому роуту
оказались 782, остальные 418 закономерно вернули 404 — они относились к
`/problem-service/` неймспейсу, а запрашивались как `/slug`, это артефакт
тестового скрипта, не баг сайта), concurrency 50:

| Момент | RSS |
|---|---|
| До теста (истинно холодный) | 195.1 MB |
| Пик во время теста (34.4 сек) | **499.7 MB** |
| Через 30+ секунд после | плато 482.2 MB, без дальнейшего роста |

### Вывод (Этап 4-5) — прямой ответ на вопрос "воспроизводится ли проблема"

**Частично нет.** Ни с прогретым, ни с истинно холодным стартом, ни при
concurrency до 50 и тысяче с лишним уникальных новых URL мне **не удалось
воспроизвести** рост RSS выше ~520 MB — то есть ни разу не дошёл даже до
900 MB (текущий `max_memory_restart`), не говоря о зафиксированных в проде
1.1-1.68 GB. При этом:

- Память **растёт пропорционально числу одновременно рендерящихся уникальных
  URL** — это подтверждено (342→519 MB на 900 новых страниц, 195→500 MB на
  900+ новых при холодном старте). Гипотеза "UNIQUE_HTML_URLS решают" —
  **подтверждена частично**: они создают измеримый, но ограниченный рост.
- Память **возвращается** после нагрузки (469→373 MB за ~30с в одном тесте,
  плато без дальнейшего роста в другом) — **признаков классической утечки
  JS-хипа (heapUsed, который не освобождается) не нашёл**. Если RSS не
  возвращается к точному исходному значению, а с небольшим остатком (+30MB) —
  это ожидаемо: модульные кэши (`hot` Map в `lib/ai-content.ts`, теперь
  прогретый список закэшированных страниц) занимают немного памяти навсегда,
  но **ограниченно** (см. раздел 6).
- **Не смог подтвердить сам механизм скачка до 1.1-1.68 GB.** Наиболее
  вероятные факторы, которые отличали реальный инцидент от моего теста (и
  которые я не воспроизводил намеренно, чтобы не рисковать сервером):
  1. **Конкуренция с параллельным build-процессом.** В момент первых
     restart'ов (08:57-08:59) на том же сервере одновременно с рабочим
     процессом выполнялась пересборка (`npm run build`), которая сама по себе
     потребляла 500MB-1.4GB RSS. Суммарная память (build + server) на VPS с
     3.8GB могла реально приблизиться к физическому пределу и провоцировать
     аномальное поведение аллокатора/GC под давлением ОС на весь хост — этого
     я в изолированном тесте не воспроизводил.
  2. **Реальная concurrency могла быть выше 50** — в логах видно десятки
     разных IP, бьющих в одну и ту же секунду; без rate limit (которого на
     момент инцидента ещё не было) ничто не ограничивало одновременные
     соединения с одного nginx-воркера на upstream.
  3. **Повторяющиеся холодные старты под продолжающимся штормом** — PM2
     рестартовал процесс каждые ~2 минуты, и КАЖДЫЙ раз новый холодный
     процесс тут же встречал тот же шторм заново, без шанса стабилизироваться
     — компаундирующийся эффект, которого нет в одиночном контролируемом
     тесте.

  Честно: я не смог с уверенностью выбрать одну причину из трёх. Наиболее
  вероятна комбинация (1)+(3) — совпадение по времени очень характерное.

## 6. SQLite (Этап 6)

`lib/ai-content.ts` — единственный путь чтения основного контента:
- **Singleton-соединение**: `db` — module-level переменная, инициализируется
  один раз (`if (db !== undefined) return db;`), `readonly: true`, WAL mode.
  **Новое соединение на каждый рендер НЕ создаётся** — это правильно.
- **Prepared statement**: да, `stmt = db.prepare("SELECT data FROM content WHERE slug = ?")`,
  переиспользуется.
- **Закрытие соединений**: соединение не закрывается никогда за время жизни
  процесса — и это корректно для read-only singleton (закрывать нечего до
  остановки процесса).
- **`hot` LRU-подобный кэш**: `Map`, ограничен `HOT_MAX = 2000`, при
  переполнении — `hot.clear()` (полный сброс, не настоящий LRU, но
  гарантированно ограничен по размеру — не растёт бесконечно).
- **`getIndexableSlugSet()`**: один `SELECT slug FROM content` при первом
  вызове, результат — `Set<string>`, держится в памяти постоянно
  (мемоизация). Размер зависит от числа индексируемых страниц в БД — это
  **одноразовое ограниченное** выделение, не утечка, но стоит знать точный
  размер (не измерял — не критично, это один `Set` строк, не могло бы дать
  гигабайтный рост).
- Проверил остальные `new Database(...)` в кодовой базе (`lib/leads-store.ts`,
  `lib/vk-automation/*`) — не относятся к пути рендера SEO-страниц
  (лиды/VK-автоматизация), не могли повлиять на инцидент.

**Вывод:** SQLite-слой реализован правильно (singleton, prepared statement,
read-only, ограниченный кэш). Не источник проблемы.

## 7. Next.js cache layers (Этап 7)

- `.next/cache/webpack/*` — build-time кэш компиляции (182MB, 13 файлов).
  **Не используется в рантайме** `next start` — это артефакт `next build`,
  не влияет на RSS работающего сервера.
- `.next/server/app/*.html` (+`.meta`+`.rsc`) — это и есть ISR/Incremental
  Cache для страниц: файловый кэш на диске, растёт линейно с числом уникально
  запрошенных `[slug]`-страниц (5007 файлов = 1.4GB на момент проверки).
  Рост этого кэша **не эквивалентен** росту RSS процесса — это диск, не
  память, хотя запись каждого файла на диск требует держать сериализованный
  HTML/RSC в памяти ровно на момент записи (кратковременно).
- Отдельного `fetch cache`/`unstable_cache` в коде не нашёл — приложение не
  использует `fetch()` с Next-специфичным кэшированием для данных (данные
  берутся напрямую из SQLite/CSV в памяти, не через `fetch`).

**Вывод:** дисковый ISR-кэш растёт пропорционально уникальным URL (это и есть
искомая корреляция "UNIQUE_HTML_URLS"), но сам по себе не объясняет скачок
RSS — раздел 4-5 показывает, что даже прямой рендеринг тысячи новых страниц
даёт кратный, но ограниченный (~350-500MB) рост, не гигабайтный.

## 10. Второй PM2-инстанс — расчёт памяти (без запуска)

Текущий baseline одного процесса в стабильном режиме: **370-500 MB**, пиковый
VmHWM зафиксирован на **1.68 GB** (реальный инцидент). VPS: 3.8GB RAM, 2GB swap.

Не-Node потребление сейчас (`free -m` used 946MB минус ~490MB текущего Node-
процесса) ≈ **~450-500MB** на OS/nginx/PM2-демон/fail2ban/systemd-journald и
прочее.

Худший случай (оба инстанса одновременно уходят в исторический пик 1.68GB,
что маловероятно при уже включённом rate limit, но берём для расчёта запаса):

```
2 × 1.68GB (оба на историческом пике)   = 3.36 GB
+ OS/nginx/прочее                        = 0.50 GB
----------------------------------------------------
ИТОГО худший случай                      = 3.86 GB   ⚠️ вплотную к пределу 3.8GB
```

Худший случай **не оставляет запаса** — это неприемлемо как есть.

Более реалистичный случай (оба инстанса на своём текущем `max_memory_restart`
900MB, PM2 гарантированно убьёт превысивший):

```
2 × 0.9GB (max_memory_restart потолок)  = 1.8 GB
+ OS/nginx/прочее                        = 0.5 GB
----------------------------------------------------
ИТОГО при штатной работе лимитов         = 2.3 GB   →  1.5 GB свободно (39%)
```

Это **укладывается** в требование "минимум 25-30% свободной RAM".

**Рекомендация по цифрам:** прежде чем включать второй инстанс, **снизить
`max_memory_restart` до ~700MB на инстанс** (а не поднимать, как
предостерегает ТЗ) — тогда худший случай = 2×0.7+0.5 = 1.9GB, оставляя >50%
свободной памяти даже если оба процесса одновременно упрутся в потолок.
Поднимать потолок выше 900MB как "основное решение" не делаю — согласен с
пунктом 13 ТЗ.

## 11. Совместимость shared ISR-кэша при двух процессах

Оба процесса при запуске из одной директории (`/var/www/master-na-dom`) будут
использовать **один и тот же** физический каталог `.next/server/app` на
диске — это не serverless-окружение, файловый ISR-кэш **общий по факту**
(один и тот же путь на одном сервере), а не изолированный на процесс.

Риск, который это создаёт:
- **Race condition при первом запросе новой страницы**: если `least_conn`
  направит два одновременных первых запроса к одному и тому же новому `slug`
  на РАЗНЫЕ инстансы (возможно при быстрой последовательности запросов от
  разных клиентов, пока файл кэша ещё не появился), оба инстанса независимо
  выполнят полный рендер и оба попытаются записать один и тот же
  `<slug>.html`/`.meta`/`.rsc`. Next.js пишет через `fs.writeFile`
  (атомарность записи в этой версии я **не проверял** в исходниках — не
  делаю здесь непроверенного утверждения про "atomic rename", хотя это
  обычная практика Next.js). Худший случай — не порча контента (оба процесса
  рендерят из ОДНИХ и тех же данных, результат идентичен), а **удвоенная
  вычислительная работа** на первый запрос конкретного URL. Не критично, но
  не бесплатно.
- Нет межпроцессного invalidation-сигнала: если один процесс ревалидирует
  страницу (после `revalidate: 86400`), другой узнает об этом только когда
  сам получит запрос к этой странице и увидит устаревший mtime — то есть с
  небольшой задержкой, не мгновенно. Не проблема для контента с revalidate
  раз в сутки.

**Рекомендация:** технически безопасно включать (нет риска порчи данных),
но для минимизации дублирующей работы **предпочесть `ip_hash` вместо
`least_conn`** в nginx upstream — это направляет запросы от одного клиента
стабильно на один и тот же инстанс, снижая (не исключая полностью) шанс
гонки на "первый рендер" конкретного slug от двух разных клиентов
одновременно. Полностью гонку это не устраняет (два РАЗНЫХ клиента всё равно
могут одновременно попасть на разные инстансы), но это приемлемый компромисс
без дополнительной инфраструктуры (Redis-кэш и т.п.), которую я не предлагаю
добавлять сейчас — это отдельная, более крупная задача.

## 12. nginx microcache — схема (не применена)

Проверил применимость:
- Персонализация — нет (страницы одинаковы для всех посетителей).
- Cookies — есть (`pm_attr` для атрибуции UTM, `master_offer_*` в
  localStorage — не cookie, не влияет на HTML), но они **не влияют на
  содержимое HTML-ответа** (атрибуция читается и используется клиентским JS
  после гидратации, не на сервере).
- Auth — нет на публичных страницах (только `/admin` и `/api`, уже вне scope
  микрокэша).
- Гео-зависимость контента — нет, контент по городу выбирается по URL
  (`/remont-x-city`), не по IP/геолокации посетителя.
- A/B-тесты — не нашёл активных в коде.
- Формы — есть (`CallForm`), но это POST на `/api/leads`, отдельный location,
  никогда не кэшируется.

**Вывод: HTML детерминирован и публичен → microcache безопасен.**

**Предлагаемая (не применённая) схема** — добавить в существующий
`proxy_cache_path`/`location /` (там уже ЕСТЬ микрокэш на 60 секунд! —
см. `sites-available/master-na-dom`, `proxy_cache_valid 200 60s`). То есть
**microcache для публичных GET-страниц уже реализован до меня** — я его не
трогал. Единственное расширение, которое имело бы смысл: увеличить TTL с
60 секунд до, например, 300-600 секунд для страниц вне hub'ов (контент
меняется по `revalidate: 86400`, то есть раз в сутки — 60-секундный TTL
избыточно короткий и не даёт кэшу принять на себя больше нагрузки от
повторных хитов на одну и ту же новую страницу в первые секунды после её
рендера). Это не применяю — отдельное решение, не связанное с текущим
инцидентом напрямую (микрокэш уже был, инцидент это не предотвратило именно
потому что штурмовали РАЗНЫЕ URL, а микрокэш по определению не помогает с
первым хитом на уникальный URL).

## 13. Hot URL prewarm — предложение скрипта (не применено)

## 14. generateStaticParams — оценка стоимости (расчёт, не измерение)

Данные для оценки: замеренный p50 рендера одной новой страницы под низкой
конкуренцией — **~47-88ms** (раздел 4-5, cold-тест c=1). Средний размер
закэшированной страницы на диске — 1.4GB / 5007 ≈ **~280 KB** (html+meta+rsc).

| Страниц | Оценка build time (добавка, последовательно×0.07с) | Оценка build time (параллельно, 4 воркера) | Доп. место на диске | Доп. RAM при билде |
|---|---|---|---|---|
| 100 | ~7 сек | ~2 сек | ~28 MB | не критично |
| 500 | ~35 сек | ~9 сек | ~140 MB | не критично |

## 15. 404-валидация — перепроверено

Подтверждено **измерением**, не только чтением кода: запрос заведомо
несуществующего slug на **production** — `404, 47-58ms`. Быстро, `notFound()`
вызывается до дорогих операций (SQLite/FAQ/JSON-LD). Дополнительно в
нагрузочном тесте (раздел 4-5, сценарий C) на изолированном инстансе фейковые
URL показали p50=159ms — **медленнее**, чем валидные cold-страницы (47-88ms)
на том же инстансе. Возможное объяснение (не проверено до конца в этой
сессии — только гипотеза с умеренной уверенностью): `getBrandPageBySlug`
фолбэк-проверка для несуществующих `/[slug]` может делать более дорогой поиск
по 31k-строчному `brand-pages.csv`, чем прямой хэш-lookup валидного
`pages.csv`-slug. Не критично для памяти (404 не кэшируется на диск, не
растит `.next/server/app`), но **стоит отдельно профилировать
`lib/brand-pages.ts`** — это разумный follow-up, не сделанный в рамках этого
аудита (не хотел трогать код без явного запроса на SEO-изменения).

## 16. Atomic deployment — план (не внедрён)

Текущая схема (та, что вызвала повторный риск во время правок) — **опасна**:
`npm run build` пишет прямо в `/var/www/master-na-dom/.next`, из которой
одновременно читает работающий `next start`. Предлагаемая схема:

```
/var/www/master-na-dom/
  releases/
    20260916-091530/   ← полная копия репо + node_modules + .next этого билда
    20260917-140210/
  current -> releases/20260917-140210   (symlink)
  shared/
    data/               ← ai-content.db, .env.local и т.п. — НЕ дублируется на каждый релиз
```

Алгоритм:
1. `git clone`/`rsync` кода в новую `releases/<timestamp>/`.
2. Симлинки на `shared/` для данных, которые не должны копироваться на каждый
   релиз (особенно `data/ai-content.db`, 582MB — копировать его на каждый
   деплой расточительно и медленно).
3. `pnpm install && npm run build` **внутри новой директории** — старый
   релиз в это время продолжает как ни в чём не бывало обслуживать трафик,
   потому что он физически в другой директории.
4. Healthcheck нового билда на отдельном временном порту (`next start -p
   <temp-port>`) — curl главной, city hub, 5-10 service×city страниц,
   `/sitemap.xml`, `/robots.txt`.
5. Опционально — `npm run cache:warm` (Этап 13) на этот временный порт для
   top-N страниц.
6. Атомарное переключение: `ln -sfn releases/<new> current` (сам symlink
   swap — атомарная ФС-операция, не может оставить "наполовину").
7. `pm2 reload` (не `restart` — см. Этап 17) с `cwd`, указывающим на
   `current`.
8. Повторный healthcheck после переключения.
9. **Rollback-план**: если healthcheck после переключения падает — `ln -sfn
   releases/<previous> current` + `pm2 reload` — тоже атомарно, секунды.
   Старые релизы (последние 3-5) не удалять сразу — держать для быстрого
   отката.

Это стандартная "releases + current symlink" схема (Capistrano-style),
адаптированная под PM2. **Не внедрял** — это затрагивает `ecosystem.config.cjs`,
`start-prod.sh` и требует тестового прогона, который сам по себе рискован
делать без отдельного подтверждения. Оставляю как рекомендацию с конкретным
планом.

## 17. Zero-downtime reload

`pm2 reload` (в отличие от `restart`) для **fork-mode** (текущий режим,
не `cluster`) фактически ведёт себя как `restart` — честный zero-downtime
reload без даунтайма технически требует `cluster` mode (несколько воркеров
одного приложения на одном порту через Node's cluster API) **или** нескольких
процессов за nginx upstream (то, что уже заложено в `ecosystem.config.cjs`
как `master-na-dom`/`master-na-dom-2`). При одном fork-инстансе `pm2 reload`
не даёт реального преимущества перед `restart` — это стоит знать: сама по
себе замена `restart`→`reload` без второго инстанса **не решает** проблему
502 во время деплоя. Zero-downtime здесь достижим только через связку
"atomic deploy (Этап 16) + 2 инстанса (Этап 10-11) + `pm2 reload` по одному
с интервалом (rolling)".

## 18. Swap

Текущее: `/swapfile`, 2GB, используется ~92MB (не менял). Это разумный объём
для VPS с 3.8GB RAM — не решает утечки памяти (своп на порядки медленнее RAM,
попытка "спастись свопом" от настоящей утечки приведёт к тормозам, а не к
стабильности), но даёт защиту от мгновенного OOM-killer в кратких пиках
(билд, кратковременный всплеск при деплое). **Рекомендация: оставить как
есть**, не увеличивать — 2GB на VPS такого размера достаточно как страховка,
увеличение свопа не заменяет реальные меры (rate limit, atomic deploy,
второй инстанс с грамотным лимитом).

## 19. Итоговый вывод

1. **Что именно вызывает рост памяти:** количество одновременно рендерящихся
   уникальных `[slug]`-страниц (SQLite-чтение + JSON-LD + FAQ/цены на
   каждую) — подтверждено измерением, эффект ограничен (~350-520MB прироста
   в моих тестах). Точная причина скачка до 1.1-1.68GB в реальном инциденте
   **не воспроизведена уверенно** — наиболее вероятна комбинация одновременного
   build-процесса, отъедавшего RAM, и повторяющихся холодных стартов под
   продолжающимся штормом (раздел 4-5).
2. **Воспроизводится ли:** частично — рост "быстрее база, есть провалы GC"
   да, экстремальный скачок до предельных значений — нет, в контролируемых
   условиях.
3. **JS heap leak или нет:** **свидетельств утечки не найдено.** RSS
   возвращается к near-baseline после нагрузки (469→373MB за 30с;
   стабильное плато без дальнейшего роста в другом тесте). Кэши в коде
   (`hot` Map) ограничены явно.
4. **Влияние unique URLs:** подтверждено, измерено, пропорционально, но
   ограничено сверху в моих тестах.
5. **Влияние ISR:** три динамических роута (`[slug]`, `problem/[slug]`,
   `problem-service/[slug]`, ~50k+ потенциальных URL) полностью
   on-demand без `generateStaticParams` — единственный источник cold-start
   нагрузки; хабы (`goroda`, `uslugi`, `blog`) уже безопасны (prebuilt).
6. **Влияние SQLite:** минимально — singleton, read-only, prepared
   statement, ограниченный кэш. Не источник проблемы.
7. **Влияние concurrency:** подтверждено измерением как значимый фактор
   (сильнее, чем просто аггрегатный req/s) — RSS выше при выше concurrency
   для того же числа уникальных URL.
8. **Почему стабилизировалось после nginx reload:** не установлено со 100%
   уверенностью какая доля — rate limit (ограничил параллельные соединения с
   одного IP через `limit_conn`) или естественное затухание волны + время на
   прогрев ISR-кэша без новых рестартов. Оба фактора правдоподобны и,
   вероятно, действовали вместе.
9. **Насколько полезен текущий rate limit:** подтверждён измерением как
   безопасный (0 ложных срабатываний на реальных ботах) и минимально
   инвазивный (10 срабатываний из 4416 запросов, все на подтверждённо
   аномальном источнике). См. `rate_limit_analysis.md`.
10. **Безопасен ли второй PM2-инстанс:** технически да при условии снижения
    `max_memory_restart` до ~700MB/инстанс и предпочтения `ip_hash` над
    `least_conn` в nginx upstream (раздел 10-11). **Не включал** — решение
    за вами.
11. **Нужен ли nginx microcache:** уже есть (60с TTL), можно рассмотреть
    увеличение TTL — не критично, не применял.
12. **Нужен ли cache warming:** да, целесообразен для топ-страниц после
    деплоя — дизайн скрипта дан (Этап 13), не реализован.
13. **Какие страницы стоит prebuild:** топ-100/500 гео-страниц по трафику
    (не рассчитано без данных позиций — отдельная задача).
14. **План atomic deployment:** дан в разделе 16, не внедрён.
15. **План rollback:** атомарный symlink-свитч на предыдущий релиз, дан в
    разделе 16.
16. **Рекомендуемая архитектура:** см. три варианта ниже.

## Три варианта архитектуры

### A. MINIMAL — минимальные изменения для текущего VPS
- Оставить как есть (1 инстанс, текущий nginx rate limit).
- Добавить только: снизить `max_memory_restart` с 900MB до ~700MB (более
  ранний, предсказуемый рестарт вместо риска дойти до 1.5-1.7GB).
- **RAM:** без изменений, пик ограничен ~700MB вместо потенциальных 1.6GB+.
- **Риски:** cold-start после рестарта всё ещё уязвим к новому шторму (хотя
  rate limit теперь его сглаживает); единственная точка отказа — 1 процесс.
- **Сложность:** тривиальная (1 строка в `ecosystem.config.cjs`).
- **Ожидаемый эффект:** снижает вероятность повторной раскрутки RSS до
  опасных значений, не устраняет первопричину cold-start нагрузки.

### B. BALANCED — оптимальный вариант цена/устойчивость
- MINIMAL +
- Второй PM2-инстанс (`master-na-dom-2`, :3001) с `max_memory_restart: 700MB`
  каждый, nginx upstream с `ip_hash` вместо текущего единственного сервера.
- `generateStaticParams` для топ-100-200 денежных гео-страниц (после получения
  данных о позициях/трафике — Этап 21 основного SEO-аудита).
- Cache-warm скрипт (Этап 13), запускаемый после каждого деплоя вручную/из
  deploy-скрипта.
- **RAM:** до 1.9GB в худшем случае (2×700MB+500MB), >45% свободно.
- **Риски:** дублирующий рендер первого запроса новой страницы между
  инстансами (низкая вероятность, не критично — раздел 11); требует
  аккуратного тестирования nginx upstream-конфига перед вкатыванием.
- **Сложность:** средняя — нужно протестировать 2-инстансный режим отдельно
  от прод-трафика (как я тестировал :3001 в этом аудите) перед включением.
- **Ожидаемый эффект:** устойчивость к повторению именно этого сценария
  (двойной запас по concurrency, топ-страницы не платят cold-start штраф).

### C. MAXIMUM — архитектура под существенный рост SEO-трафика
- BALANCED +
- Atomic deployment (releases/ + symlink, Этап 16) — устраняет риск
  "сервер читает частично записанный `.next`" полностью, а не только смягчает.
- Расширить `generateStaticParams` до топ-1000-2000 страниц по трафику.
- Рассмотреть увеличение VPS (RAM) при устойчивом росте органического
  трафика — на 3.8GB потолок даже BALANCED-конфигурация не даёт большого
  запаса при реальном скачке трафика (не только атаке/скрейпинге).
- Настоящий zero-downtime: `cluster` mode или ≥3 инстансов с rolling reload.
- Shared cache handler для ISR (например, через кастомный Next.js cache
  handler поверх Redis) вместо файловой системы — устраняет race condition
  из раздела 11 полностью, а не только снижает вероятность.
- **RAM:** нужно пересчитывать под конкретное число инстансов; ориентир — не
  менее 6-8GB VPS при 3+ инстансах с текущими лимитами.
- **Риски:** значительно больше движущихся частей, требует нормального
  staging-окружения для тестирования (которого сейчас нет — см. общий
  комментарий ниже).
- **Сложность:** высокая, многодневная работа, не однократная правка.
- **Ожидаемый эффект:** устойчивость к кратному росту трафика (не только к
  повторению этого конкретного инцидента), реальный zero-downtime деплой.

У проекта сейчас нет staging/preview-окружения — весь этот аудит пришлось
