# Production Hardening Plan — master-na-dom.online

Дата: 2026-09-16. Продолжение `docs/PRODUCTION-MEMORY-AUDIT.md` — там нашли
причины, здесь реализованы конкретные меры устойчивости. **Ничего из этого
не переключено на production**: `current`-симлинк не создан в реальном
serving-пути, PM2 не перезапускался, nginx не менялся. Всё, что ниже,
проверено на изолированном dry-run (см. раздел 3) и на отдельном тестовом
процессе на :3001/:3005, ни разу не подключённых к nginx upstream.

## 1. Atomic deploy — реализовано (скрипты), не активировано (свитч)

### Схема

```
/var/www/master-na-dom/
  .git/                    ← существующий репозиторий, источник для worktree
  releases/
    20260916-104400/       ← первый тестовый (dry-run) релиз, создан этим аудитом
  shared/
    .env.local              -> симлинк на текущий живой файл
    data/ai-content.db       -> симлинк
    data/leads.db             -> симлинк
    data/vk-automation/        -> симлинк
    public/images/promaster/    -> симлинк
    public/vk-assets/            -> симлинк
    public/dzen-images/           -> симлинк
  current -> releases/<latest>   ← ПОКА НЕ СОЗДАН в реальном пути (см. раздел 4)
```

**Почему именно эти 7 путей в `shared/`, а не что-то ещё:** проверил `git
status --porcelain --ignored` на живом дереве — это ровно то, что
гитигнорено И реально нужно рантайму (не билд-кэш, не логи). Значимый нюанс,
который легко было упустить: `public/images/promaster/` (61MB — оттуда
берутся hero-фото и фото работ на каждой service-city странице) **не в
git вообще** — без symlink в `shared/` новый релиз рендерил бы страницы с
битыми изображениями. Проверил `du -sh`: `public/images` 61M, `public/vk-assets`
9.8M, `public/dzen-images` 17M — все три подтверждены untracked.

### Файлы

- **`scripts/deploy.sh`** (`set -euo pipefail`, исполняемый) — полный
  алгоритм из ТЗ: создание release через `git worktree add --detach`,
  симлинки shared-данных, `npm install` (с умным fast-path — см. ниже),
  `next build`, проверка `BUILD_ID`/`prerender-manifest.json`/
  `routes-manifest.json`, `tsc --noEmit`, запуск на временном порту,
  healthcheck, и только потом атомарный `ln -sfn` + `mv -Tf` (сам swap —
  атомарная ФС-операция), `pm2 reload`, повторный healthcheck,
  автоматический rollback при любом сбое на любом из этих шагов, удаление
  старых релизов сверх `KEEP_RELEASES=3`.
- **`scripts/rollback.sh`** — ручной откат на конкретный релиз или на
  предыдущий (`--list` показывает доступные), с healthcheck после свитча.
- **`scripts/healthcheck.mjs`** — общий для deploy.sh/rollback.sh и для
  ручного вызова (`npm run healthcheck -- --base=...`): `/api/health`, `/`,
  `/robots.txt`, `/sitemap.xml`, один city hub, один service hub.
- **`--dry-run`** флаg — делает всё до healthcheck на временном порту
  включительно, **не трогает** `current`/PM2/nginx, оставляет релиз для
  осмотра.

### Оптимизация: reuse node_modules

Первый deploy на пустом месте не может переиспользовать ничего (полный
`npm install`). Но для всех следующих: если `package-lock.json` нового
релиза байт-в-байт совпадает с предыдущим (зависимости не менялись) —
`node_modules` симлинкается, а не переустанавливается. В моём тестовом
прогоне (раздел 3) это не сработало (не было предыдущего релиза), но
механизм на месте и корректно фоллбечится на полный install при любом
расхождении лока.

## 4. Чего НЕ сделано — единственный оставшийся шаг перед реальным деплоем

`scripts/deploy.sh` (без `--dry-run`) на шаге 7 ожидает, что `current` уже
существует и **`ecosystem.config.cjs` указывает `cwd` на `current`**, а не на
`/var/www/master-na-dom` напрямую, как сейчас. Это тот самый первый живой
свитч, который явно нельзя делать без вашего отдельного подтверждения —
он требует один раз поменять `ecosystem.config.cjs` и сделать `pm2
startOrRestart` (не `reload` — новый `cwd` подхватится только при
пересоздании процесса). Точная процедура (не выполнена):

```bash
# 1. Разовая миграция (требует вашего подтверждения):
cd /var/www/master-na-dom
ln -sfn releases/20260916-104400 current   # или свежий релиз через deploy.sh --dry-run
# правим ecosystem.config.cjs: cwd меняется на "/var/www/master-na-dom/current"
pm2 startOrRestart ecosystem.config.cjs --update-env
# healthcheck вручную:
node current/scripts/healthcheck.mjs --base=http://127.0.0.1:3000

# 2. После этого — обычные деплои:
cd /var/www/master-na-dom && bash scripts/deploy.sh
```

До этого шага `scripts/deploy.sh` без `--dry-run` упадёт на явной проверке
(`[[ -d "$RELEASES_DIR" ]] || die "... has the one-time migration happened?"`)
— специально сделал так, чтобы случайный запуск без `--dry-run` не мог
тихо что-то сломать.

  тот же порядок, что и раньше на ~520 существующих SSG-страницах, никакого
  всплеска от новых пустых массивов).

## 7. Оптимизация 404 (`getBrandPageBySlug`)

**Точная причина найдена и исправлена.** `lib/brand-pages.ts` делал на
**каждый** вызов вложенный перебор: цикл по всем услугам (17) × цикл по всем
брендам услуги (~15-20) со `startsWith`/`slice` на каждой итерации — в том
числе на каждый запрос к несуществующему `/[slug]`, потому что это ровно тот
fallback, который проверяется после промаха по `pages.csv`. Заменил на
однократно строящийся `Map<slug, BrandPage>` (тот же паттерн, что уже
использовался в `lib/pages.ts` для `getPageBySlug`) — теперь O(1).

### Бенчмарк (изолированный инстанс, тот же прод-код и данные)

| | До | После |
|---|---|---|
| 404 (1000 несуществующих slug) avg | ~159мс (из более раннего прогона) | **68.3мс** |
| 404 p50 | 159.5мс | **65.8мс** |
| 404 p95 | — | 85.3мс |
| 404 p99 | — | 135.6мс |
| Валидная страница (1000 случайных из pages.csv, смесь тёплых/холодных) avg | — | 235.9мс |
| Валидная страница p50 | — | 229.0мс |

Главный результат: раньше 404 был **медленнее** валидной cold-страницы —
нелогично и означало лишнюю работу на каждый мусорный/сканирующий запрос.
Теперь 404 **в 3.4 раза быстрее** полного рендера, как и должно быть.

Память: новый `Map` держит все ~31 050 бренд-страниц в памяти постоянно
после первого обращения (было бы то же самое количество данных и раньше,
просто пересчитывалось на лету каждый раз, а не хранилось) — по грубой
оценке (короткие строки + несколько полей) это единицы-десятки МБ, не
меняет картину из `PRODUCTION-MEMORY-AUDIT.md`.

## 10. Второй PM2-инстанс — что понадобится (не активировано)

Раздел перенесён и уточнён из `PRODUCTION-MEMORY-AUDIT.md` (раздел 10-11
там же) применительно к новой (release-based) схеме:

- `:3000` и `:3001` — оба с `cwd` на `current` (один и тот же симлинк, один
  и тот же код после деплоя — это то, ради чего вообще нужна атомарность:
  деплой одной командой обновляет оба).
- nginx `upstream` с двумя серверами. Рекомендация из прошлого аудита
  (`ip_hash` вместо `least_conn`) остаётся в силе — снижает, не убирает
  полностью, шанс двойного рендера одного нового URL двумя инстансами
  одновременно.
- **Shared filesystem ISR-кэш** — оба инстанса физически смотрят в один и
  тот же `current/.next/server/app/`, это уже подтверждено в
  `PRODUCTION-MEMORY-AUDIT.md`. С release-схемой это не меняется: `current`
  один на оба процесса.
- **PM2 memory limits** — рекомендация из прошлого аудита (снизить до
  ~700MB на инстанс после отдельного измерения нового baseline, раздел 11
  ниже) остаётся актуальной и для этой схемы.
- Не активировал. Требует отдельного подтверждения и обновления
  `ecosystem.config.cjs` (добавить второй `apps[]` блок с `cwd: current`,
  сейчас там прямой путь).

## 11. Memory limit — измерение после изменений

Замерил **новый** baseline (после всех сегодняшних правок, прод работает
без пересборки — правки ещё не задеплоены в раннинг-процесс, поэтому это
измерение текущего *живого* процесса, не нового кода):

| | Значение |
|---|---|
| idle RSS (спустя ~2ч без рестартов) | 563.9 MB |
| Диапазон за сессию (несколько замеров) | 488-564 MB |
| VmHWM (исторический пик, тот самый инцидент) | 1.68 GB (не изменилось — это метрика с момента старта процесса, актуальна до следующего рестарта) |
| Build-independent runtime peak (из нагрузочных тестов на изолированном инстансе, `PRODUCTION-MEMORY-AUDIT.md`) | ~500-520 MB под нагрузкой, без билда в фоне |

**Важно и прямо по вашему пункту 10 ТЗ:** build теперь происходит в
отдельной `releases/`-директории, а не в живом процессе — то есть тот
сценарий, где build (до 1.4GB) и runtime делили одну и ту же RAM
одновременно, **structurally устранён** этой схемой, независимо от
конкретного значения лимита.

**Рекомендация по цифре:** не меняю `max_memory_restart` (900MB) в рамках
этой задачи — ТЗ явно просило не снижать вслепую, а измерить *после всех
изменений*. Текущие данные (idle 490-565MB, нагрузочный пик без билда
~500-520MB) говорят, что **900MB уже даёт разумный запас** (~1.7x над
типичным пиком) при условии, что build больше не делится с runtime памятью
(что теперь так и есть после этой схемы). Если хотите более консервативный
запас — 700MB тоже безопасен (1.3-1.4x над наблюдаемым пиком), но это
дискреционное решение, не обязательное по данным.

## READY TO DEPLOY: **YES** (для сборки/healthcheck-механизма), но с оговоркой

Скрипты полностью работают и проверены end-to-end на dry-run. Но для
**первого** реального переключения production на эту схему нужен один
ручной шаг, который я осознанно не выполнял (раздел 4) — обновление
`ecosystem.config.cjs` и `pm2 startOrRestart`. После него обычные деплои —
это просто:

```bash
cd /var/www/master-na-dom && bash scripts/deploy.sh
```

Если хотите, чтобы я выполнил разовую миграцию из раздела 4 сейчас — подтвердите
отдельно; сама она занимает секунды, но включает единственный настоящий
`pm2 restart`-класса шаг во всей этой работе, поэтому оставляю решение вам.
