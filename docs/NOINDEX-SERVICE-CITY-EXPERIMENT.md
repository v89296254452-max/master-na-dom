# Noindex SERVICE_CITY Experiment

Дата: 2026-09-16. **Ничего не задеплоено, noindex не снят, IndexNow не
отправлен.** Ниже — диагностика логики, категоризация 856 страниц, отбор
30/30 и честная оценка того, что реально готово.

## Точная логика noindex (код, не предположение)

Единственное условие для всех трёх динамических коммерческих роутов
(`[slug]`, `problem/[slug]`, `problem-service/[slug]`):

```ts
// app/(site)/[slug]/page.tsx (и аналогично в двух других роутах)
const ai = getAiContent(page.slug);          // lib/ai-content.ts → SQLite ai-content.db
const hasUnique = !!(ai && ai.paragraphs && ai.paragraphs.length >= 4);
return { ..., robots: { index: hasUnique, follow: true } };
```

Условие одно, бинарное: **есть ≥4 абзаца уникального ИИ-текста в
`ai-content.db` → index; нет → noindex.** Никакой отдельной логики
NO_SERVICE_CONTENT/THIN/DUPLICATE в коде не существует — это не «несколько
причин», а один и тот же гейт для всех.

## Категоризация 856 SERVICE_CITY noindex-страниц

Проверил РЕАЛЬНОЕ количество абзацев в `ai-content.db` для каждой из 856
(`scripts/seo/categorize-noindex.ts`, реальный прогон на сервере):

| Категория | Кол-во абзацев | Count |
|---|---|---|
| NO_UNIQUE_TEXT | 0 | **856 (100%)** |
| THIN (1-3, почти достаточно) | 1-3 | 0 |

**Все 856 — буквально без единого сгенерированного абзаца**, не «почти
готовые» страницы. FAQ (`hasFAQ`) и цены (`hasPrices`) при этом присутствуют
у ВСЕХ 856 (они берутся из `data/pages.csv`, не из ИИ-гейта) — то есть
страницы технически не «пустые», им не хватает конкретно уникального
описательного текста.

## Сколько из 856 реально заслуживают индексации

Не все 856 равноценны. Приоритизировал по `internalLinksIn` (сколько других
страниц сайта уже на них ссылаются — прокси реального места в архитектуре
сайта) и по размеру/узнаваемости города. Обнаружил явный лидирующий кластер:

**12 крупных городов (Москва, Тверь, Рязань, Владимир, Калуга, Курск,
Смоленск, Тамбов, Тула, Липецк, Ярославль, Брянск) × 3 услуги (Дезинфекция,
Клининг, Сборка мебели) = 36 страниц с internalLinksIn=157** — самое высокое
значение во всём noindex-пуле (для сравнения: типичная noindex-страница
"Ремонт холодильников" в среднем городе имеет internalLinksIn=57). Это
показывает, что данный кластер уже структурно приоритизирован сайтом
(больше внутренних ссылок), но не имеет текста. **Москва** в этом списке —
самый крупный город на сайте вообще, отсутствие уникального контента для
клининга/дезинфекции/сборки мебели там — заметный пробел.

Не могу дать точную цифру "сколько из 856 заслуживают индексации" без
данных о реальном поисковом спросе по каждому — у 856 страниц по
определению нет измеримой Яндекс-позиции (они noindex), и в имеющейся
выгрузке позиций (372 запроса) эти конкретные комбинации город+услуга не
отслеживались. Честная оценка: **как минимум эти 36 (топ-кластер) —
обоснованные кандидаты** по структурному сигналу (внутренние ссылки, размер
города); для остальных ~820 нужна оценка спроса (Wordstat/Метрика), которой
у меня нет.

## Усиление 30 experimental страниц — что реально готово

**Инфраструктурно готово:** гейт индексации уже правильный и не требует
изменений в коде — как только в `ai-content.db` появится ≥4 абзаца для
конкретного slug, `robots.index` станет `true` автоматически при следующей
регенерации metadata (никакого дополнительного кода не нужно).

**Не готово и не сделано в этой сессии — контент.** У проекта уже есть
рабочий механизм: `scripts/generate-ai-content.mjs` (ИИ-генерация через
OpenRouter/Claude, читает `data/pages.csv`/`problems-cluster.csv`/
`brand-pages.csv`, пишет в `data/ai-content.json`, дедуп по уже
сгенерированным). **Я не могу запустить его сам**: по комментарию в самом
скрипте, OpenRouter блокирует IP российских серверов — скрипт должен
запускаться локально с вашей машины (с `.env.generation`, не хранящимся в
репозитории). Я НЕ стал генерировать текст вручную/заглушками — это прямо
запрещено вашим ТЗ ("не генерировать бессмысленный текст ради
уникальности") и потребовало бы реальных знаний о городе/услуге, которых у
меня нет и которые нельзя честно выдумать.

**Рекомендуемая команда для вас** (не выполнял):
```bash
# локально, с чистого не-РФ IP, после настройки .env.generation
node scripts/generate-ai-content.mjs --source=geo --limit=30 \
  --shards=... # либо точечно отфильтровать pages.csv на 30 нужных slug
node scripts/build-ai-content-db.mjs   # пересобрать ai-content.db из JSON
```
После этого — пересобрать сайт (через `scripts/deploy.sh`, не вручную в
живой директории, см. `docs/PRODUCTION-HARDENING-PLAN.md`) и проверить, что
`robots.index=true` для всех 30.

**Что НЕ буду делать даже после появления текста:** использовать историю
города/население/климат не по адресу (см. service-aware фикс климат-клаузы
ниже) — для Дезинфекции/Клининга/Сборки мебели климатическая вставка и так
уже исключена этим фиксом.

## Cannibalization / дубли для 30 experimental

Не проверял попарно все 30 × весь корпус (как и в Wave 1 — см. методологию
там). Структурная проверка: каждая из 30 — уникальная комбинация
город+услуга, URL не пересекается ни с одной существующей индексируемой
страницей. Явного риска не вижу, но не подтверждаю на 100% отсутствие
семантического пересечения с BRAND/PROBLEM_SERVICE вариантами этих же
город+услуга (та же оговорка, что в `docs/SEO-GROWTH-WAVE-1.md`, раздел 4).

## Post-deploy monitoring plan (после будущего деплоя — не сейчас)

Точки замера: **день 0, 3, 7, 14, 21, 28** после деплоя + реального
появления контента у 30 experimental.

Для каждой точки, отдельно experimental vs control:

| Метрика | Источник | Приоритет |
|---|---|---|
| **INDEXATION RATE** — доля URL, реально попавших в индекс (`site:` / Яндекс.Вебмастер "Индексирование → Все страницы") | Яндекс.Вебмастер | Главный KPI |

| **KEYWORDS PER URL** — по скольким разным запросам страница получает показы | Яндекс.Вебмастер | Третий KPI |
| Средняя позиция | Топвизор/Вебмастер | Дополнительно |
| Клики | Метрика/Вебмастер | Дополнительно |

Control group должна оставаться `noindex` весь период — это гарантирует,
что рост experimental не объясняется общим ростом сайта (тот же принцип,
что и в Wave 1).

**Не отправлять IndexNow до деплоя.** После деплоя — точечно, только 30
experimental + 3 Wave-1 URL (не весь sitemap), см. `docs/PRODUCTION-
HARDENING-PLAN.md` про точечный режим `/api/admin/indexnow` (`{urls:[...]}`).
